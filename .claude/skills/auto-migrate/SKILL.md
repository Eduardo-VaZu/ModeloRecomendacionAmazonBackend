# Auto-migrate on model changes

Any change to a file under `backend/src/persistency/database/models/` — adding a model, adding/removing a field, changing a type, changing a constraint (`ge`, `max_length`, nullability), changing a primary/foreign key, or renaming — **must** be followed by an Alembic migration. The model file alone changes the Python schema; the database schema only changes when a migration runs.

## What to do, every time

1. Finish the model edit.
2. If the new model is a brand-new entity, re-export it from `backend/src/persistency/database/models/__init__.py` — otherwise Alembic's autogenerate won't see it.
3. Run the make target:
```
   make add-migration name="<short_snake_case_description>"
```
   Examples: `name="add_vehicle_telemetry_table"`, `name="zone_entered_enum"`, `name="battery_pct_constraint"`.
4. **Read the generated file** in `backend/src/alembic/versions/`. Autogenerate is good but not perfect — verify:
  - Column types match what you intended.
  - For `ALTER COLUMN ... TYPE` on existing data, a `postgresql_using="<col>::<new_type>"` clause is present, or the column was empty.
  - Enum types appear as `sa.Enum('VAL_A', 'VAL_B', name='enum_name')` and the values match your `StrEnum`.
  - Index creates/drops are intentional.
5. Apply on the running stack — the `migrations` compose service runs `alembic upgrade head` on `make up`, or run `docker compose exec backend uv run alembic upgrade head` directly.

## What runs under the hood

`make add-migration name=...` expands to:
```
docker compose exec backend bash -c "uv run alembic revision --autogenerate -m '<name>'"
```
which executes inside the `backend` container where:
- `alembic/env.py` imports `src.persistency.database.models` (so every re-exported model is registered on `SQLModel.metadata`).
- `target_metadata = SQLModel.metadata`.
- `sqlalchemy.url` is read from `POSTGRES_URL` via `ConfigurationVariables`.

The autogenerated revision lands in `backend/src/alembic/versions/` on the host because that directory is bind-mounted from the host.

## Preconditions
- The stack must be running (`make up`) so the container exists and the DB is reachable for the schema diff.
- The DB must be at the previous head before generating, or Alembic will diff against a stale state.

## Common gotchas
- **Empty migration generated** → the model isn't reachable from `models/__init__.py`. Add the import and re-run.
- **Migration drops a table you didn't touch** → another model file got renamed/deleted without re-exporting; check `__init__.py`.
- **Type change leaves rows unconvertible** → autogenerate omits `postgresql_using`. Add it manually before `alembic upgrade head`.
- **Enum value renames don't autogenerate cleanly** → Postgres native enums require explicit `op.execute("ALTER TYPE ... RENAME VALUE ...")` calls. Edit the file by hand.

## When NOT to skip
You can skip the migration step **only** for:
- Adding/changing model-level docstrings, comments, or `from __future__ import annotations`.
- Pure type-hint reformatting that doesn't change the SQLAlchemy column (e.g. `Optional[str] → str | None` where the column was already nullable).
- Adding non-persisted Python helpers (classmethods, properties) that aren't `Field(...)`.

If you're not certain whether a change is schema-affecting, run `make add-migration` anyway — autogenerate will produce an empty `upgrade()` body, which you can then delete or keep as a no-op marker.

After any schema-affecting edit under `backend/src/persistency/database/models/` (new model, new/removed field, type or constraint change, rename), proactively run `make add-migration name="<short_snake_case>"` to generate the Alembic revision, and then read the generated file in `backend/src/alembic/versions/` to verify correctness before stopping.

**Why:** Editing the SQLModel changes only the Python schema; the DB schema only changes when a migration runs. The user noticed I had altered `zone_entered` from a free `str` to a `Zone` enum without producing a migration, and explicitly asked that I do this automatically going forward.

**How to apply:** Triggers on any edit/add under `backend/src/persistency/database/models/`. Skip only for non-schema changes (docstrings, type-hint reformatting that doesn't change the SQLAlchemy column, non-`Field(...)` helpers). When in doubt, still run it — autogenerate produces an empty body when there's no diff, which is informative.
